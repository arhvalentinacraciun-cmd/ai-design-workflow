Brewlog design system

The components Brewlog is built from, rendered live from its own stylesheets, with the tokens behind each one, the rules for using it, and the code to copy.

Version 2.09 componentsAtkinson Hyperlegible Next + IBM Plex Mono

Overview

A small, complete system: three files, nine components, one rule. Everything on this page is rendered from the same stylesheets the product loads, and every value shown is read live from them.

How it is built

tokens.cssLayer 1, the primitives. Colour scales, spacing, type, shape, depth, motion. The only file that holds literal values.
component-tokens.cssLayer 2, one namespace per component. Every token points at a primitive. A theme would override this layer and nothing else.
components.cssThe components. Colour and radius only through Layer 2; spacing, type and the other shared scales directly from Layer 1.

The one rule

No literal style values outside the primitives file. Every colour, size, radius, shadow and font value is a token reference, and an automated check on every change sends any literal back to be fixed. The rule is what lets a single primitive change move the whole product at once.

Principles

  • Few things, finished. Nine components, each with its states, tokens, usage and accessibility done. A new component earns its place by being needed twice.
  • Tokens are the interface. Change a primitive and the product changes; change a component token and one component changes. Nothing else is a styling surface.
  • Native before custom. Buttons, selects, labels and radios do their own work. The system restyles and never replaces what the browser already does well.
  • Words carry meaning, colour reinforces it. A status has a word, a rating has a label, an error has a message.

Use it in a page

Load the three files in this order, then the page's own layout stylesheet. The fonts are Atkinson Hyperlegible Next for text and IBM Plex Mono for labels, counts and dates, both from Google Fonts, each with a system fallback.

How to use it

  • Build only from the component inventory. A component that is not on this page does not exist; the Adding a component section says how to add one.
  • Need a value that has no token? Propose the token, never the literal.
  • Icons are inline SVG, stroked in the current text colour, sized by the icon token. There is no icon set; a component that needs an icon brings its own path.
  • Read a component's Usage tab before its Code tab. The code is the easy part.

Colour

Seven hues, ten steps each, from 50 (lightest) to 900 (darkest); the neutral scale starts at white. Indigo is the primary: actions, links, focus, filled rating dots, and at 900 the ink itself. Lime is the accent, a highlighter rather than a text colour: it fills the brew count, a top score and the empty-state band, always with the ink on it. Roast is the coffee brown, used for the roast level and nothing else. The neutrals are cool greys from the paper to the ink; the three semantic hues are green, a burnt orange and a crimson. Components never name these directly for colour; they name a component token that points here. The step numbers carry meaning: 50 to 100 are backgrounds, 500 to 600 are fills, 700 to 900 are text on light backgrounds.

Spacing

A four-pixel base unit. Every gap, padding and margin sits on this scale, so two components placed together always share a rhythm. The number in the name is the multiple of the base unit.

Typography

Two families: Atkinson Hyperlegible Next for everything read, IBM Plex Mono for labels, counts, dates and codes, each with a system fallback. Seven sizes from 14 pixels up, four weights, two line heights. Nothing on the page is smaller than 14 pixels, and emphasis comes from weight, never from a size outside the scale.

Shape and depth

Corner radii, shadows and border widths. Radius grows with the size of the thing it rounds, up to the full pill on buttons and badges; shadows are tinted with the ink and reserved for surfaces that sit on the page. Borders that carry meaning are two pixels wide; the hairline is for dividers and decorative edges only.

Motion, layout, focus

Three durations and one transition cover every component; nothing in the system animates for decoration. Fast and base are for state changes, slow is one turn of a spinner. The remaining primitives size the reading column, the inline icons, the focus ring and the disabled state. Reduced-motion preferences are respected everywhere.

Button

Stable

The action in a view. One primary per screen; everything else steps down.

Shape and type

Ghost
Danger

Do

  • Primary for the one main action of the view, such as Add entry.
  • Secondary for actions that matter but are not the point of the view, such as Clear all. It is drawn, not filled: white with the ink outline.
  • Ghost for a quiet action next to a stronger one, such as Cancel.
  • Danger only when the action destroys something and cannot be undone.
  • Labels say what happens: Add entry, Delete entry, Save and close.

Do not

  • Two primary buttons in one view. If two actions compete, one of them is secondary.
  • Danger for destructive-but-recoverable actions. Those take secondary plus a confirmation.
  • Submit, OK or Click here as a label.
  • A disabled button with no explanation. If it cannot be used yet, say why next to it.
  • A link styled as a button for navigation, or a button for navigation. Links go places; buttons do things.
  • Always a real button element, with type set, so it works with keyboard and assistive technology by default.
  • The focus ring is part of the component and is never removed. It sits outside the button on an offset, so it reads on any background.
  • Icon-only buttons carry an aria-label with the action in words. Decorative icons are aria-hidden.
  • A loading button sets aria-busy and keeps its width, so the layout does not jump and the state is announced.
  • Disabled buttons use the native disabled attribute, which also removes them from the tab order.

Input

Stable

A single line of text with its label, hint and error. The label is part of the component, not an optional extra.

Component tokenPoints atLive value
Input
Field text

Do

  • Free text that fits on one line: a name, a roaster, an origin.
  • A placeholder as an example of the format, never as the label.
  • A hint for anything the label cannot say in two words.
  • An error that says what to do, under the field it belongs to.

Do not

  • Drop the label to save space. A placeholder disappears the moment someone types.
  • Use it for a fixed set of choices. That is a Select.
  • Colour alone for an error. The message is the error; the border only points at it.
  • Disable a field to mean read-only. Show the value as text instead.
  • The label's for attribute matches the input's id, so clicking the label focuses the field and screen readers announce it.
  • Hints and errors are linked with aria-describedby and read after the label.
  • An invalid field sets aria-invalid, which screen readers announce; the red border is for sighted users.
  • The required marker is visual only; the required attribute carries the meaning.
  • Placeholder text holds contrast against white, but still never stands in for a label.
  • Focus is the shared ring plus the border colour, the same signal a button gives.

Select

Stable

One choice from a fixed list. It looks and behaves exactly like Input, with a chevron drawn by the system instead of the browser.

Component tokenPoints atLive value

Do

  • Six or more options, or options with longer labels.
  • A choice that is set once inside a form and submitted with it.
  • A sensible default selected, so the field is never blank without reason.

Do not

  • Two to five short options that switch a view instantly. That is the segmented control's job.
  • A placeholder option with no error handling. If Choose a roast is left, say so on submit.
  • A custom dropdown built from divs. The native control handles keyboard, screen readers and phones.
  • Native select: keyboard, screen reader and mobile pickers come for free, and the system only restyles the box.
  • Label wired by for and id, hint and error by aria-describedby, exactly as Input.
  • The chevron is drawn by the wrapper and ignored by assistive technology; the control still announces as a combo box.
  • An invalid select sets aria-invalid; a disabled one uses the disabled attribute.

Badge

Stable

A status, read at a glance. Pill-shaped, coloured by meaning.

Component tokenPoints atLive value
Shape
Variants

Do

  • Status and counts: Saved, Unrated, 3 brews.
  • Accent, the lime, for the one number on the page, such as the brew count. One accent badge per view.
  • One or two words. A badge is read, not studied.
  • The colour means something. Success is green because it is good news.

Do not

  • A badge for metadata such as a roast level or an origin. That is a Tag.
  • A clickable badge. It reports; it does not act.
  • Several badges on one item. One status at a time.
  • Each variant pairs a 100 background with a 700 text colour from the same hue, which holds contrast at the small size. Accent is the exception: a lime fill with the ink on it, because no lime step is dark enough to be text.
  • The word carries the meaning; the colour and the dot reinforce it. Never a colour-only badge.
  • A badge is plain text in a span, so it needs no role.

Tag

Stable

A piece of metadata attached to an entry: roast, origin, process. Quiet by design.

Component tokenPoints atLive value
Tag
Roast
Remove

Do

  • Facts about an entry that help you find it again.
  • Several in a row; they are meant to sit together.
  • Plain inside a card, where a pill would fight the card edge. The roast level is a plain tag with a dot.
  • Removable when the person added it and may change their mind.

Do not

  • Colour a tag to show status. Status is a Badge. The roast colour is not status: it is the coffee, and brown appears nowhere else.
  • A selected look for filtering. Filtering is the segmented control's job.
  • A removable tag with no way to add one back.
  • Plain text in a span; it needs no role.
  • The remove button carries the tag's text in its aria-label, so Remove alone is never announced.
  • The remove button keeps the shared focus ring and a hit area the size of an icon.

Card

Stable

A white surface that groups related content, lifted off the page by its shadow. Header and footer are optional rows with their own divider.

Component tokenPoints atLive value
Surface
Text

Do

  • One card per thing in a list: one entry, one brew.
  • Header for the name and its status, body for the content, footer for actions.
  • Interactive only when the whole card is one target. Then it is focusable and has one action.

Do not

  • Nested cards. A card inside a card means the inner one should be a plain group.
  • A card to decorate a single paragraph. Surfaces group; they do not emphasise.
  • Several buttons inside an interactive card. Nested targets confuse keyboard and touch.
  • A card is a div; the list around it gives the structure.
  • An interactive card is focusable (tabindex or a link), shows the focus ring, and has exactly one action.
  • The title is a heading at the right level for the page; the meta line is plain text.
  • A rating inside a card carries an aria-label with the score in words.

Alert

Stable

A message about the current state of the page: empty, saved, a warning, a problem.

Component tokenPoints atLive value
Shape
Variants

Do

  • Info for an empty state, with an invitation to act. It is the lime band: the one thing on an empty page to notice.
  • Danger for an error, saying what went wrong and how to fix it. No apology, no mystery.
  • A title when the message has two parts: what happened, what to do.
  • Actions inside the alert when the fix is one click away.

Do not

  • Stacked alerts. One at a time, the one that matters now.
  • An alert as a heading or a callout for ordinary text.
  • A dismiss button on an error. The error goes away when it is fixed.
  • Vague wording. Something went wrong is not a message.
  • Info, success and warning use role status, announced politely when they appear; danger uses role alert, announced at once.
  • Each variant pairs a light background with a dark text colour from the same hue and holds contrast at body size; info pairs the lime band with the ink.
  • The dismiss button has an aria-label and the shared focus ring.
  • Actions inside an alert are real buttons, in reading order after the message.

Rating

Stable

Five dots, filled to the score. How much you liked a brew, on your own scale. Empty dots are outlined, so the score reads at any size; a full score sits on the highlighter band.

Component tokenPoints atLive value

Do

  • A personal score in a private journal. Dots say how much I liked it; stars would read as a public review.
  • Always five dots, so an unrated entry still reads as a rating.
  • The label when the number matters, such as a detail view.

Do not

  • Interactive dots. The score is entered through the Select in the form.
  • Half dots. The scale is whole numbers.
  • Stars, hearts or thumbs. One shape, one meaning.
  • The group has role img and an aria-label with the score in words. Without it, a screen reader hears five empty spans.
  • Filled dots are solid, empty dots are outlined: the score reads without colour and at the smallest size.
  • The optional label is aria-hidden because the group already announces the score.

Accessibility

What every component promises, so that a page built only from the system starts from a sound floor. Each component's own tab lists the specifics.

Commitments

  • Native first. Buttons are buttons, selects are selects, labels are labels. The system restyles; it does not reinvent.
  • Visible focus, everywhere. One focus ring, one colour, one width, on every focusable element. Nothing removes it.
  • Contrast by construction. Text pairs are chosen from the scales so that body-size text holds 4.5 to 1 and large text 3 to 1; the smallest text on any page is 14 pixels, and grey text at that size sits above 7 to 1 because anything fainter reads grey on a laptop. The tables on each component measure the live pairs, so a token change that breaks a pair shows up here.
  • Never colour alone. Status has a word, a rating has a label, an error has a message. Colour reinforces; it does not carry.
  • Reduced motion respected. The only animation, the loading spinner, slows down under a reduced-motion preference, and smooth scrolling turns off.
  • Labels linked, messages linked. for and id for labels, aria-describedby for hints and errors, aria-invalid for invalid fields, aria-busy for loading.

Adding a component

The same five steps every time, in this order. Each step is checkable; the hook checks the first three for you.

  1. Story first. A Markdown file in stories/: what it is, when to use it and when not, anatomy, states, the tokens it needs, accessibility, acceptance criteria. The segmented control story is the template.
  2. Tokens. Add the component's Layer 2 tokens to component-tokens.css, each pointing at a primitive. Every colour and radius goes through them. A literal value anywhere comes straight back from the hook.
  3. CSS. Add the classes to components.css, using only the new tokens and the shared scales. Include hover, focus, disabled and any error state the story names.
  4. Inventory. Add a row to the design-system skill at .claude/skills/design-system/SKILL.md. Until the row exists, the agent treats the component as not existing, which is correct.
  5. This page. Add a component block here with the five tabs: preview specimens (each one a template, which also becomes its code), the token table, usage, accessibility with its contrast pairs, and a changelog line. Copy the Button block and replace its content. Then move the component's link in the nav out of the planned style.

Then open Brewlog next to this page, change one primitive in tokens.css, and reload both. If the new component moved with everything else, it is part of the system.
