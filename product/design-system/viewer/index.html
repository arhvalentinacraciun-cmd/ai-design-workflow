Button

The action in a view. One primary per screen; everything else steps down.

Variants

States

Tab through the stage above: every button shows the shared focus ring, offset by one spacing step. Hover and active states are not styled on purpose; the transition token is in place for when a state is added, and that is a design decision, not a CSS afterthought.

Tokens

Component tokenPoints atLive value

Usage

Use

  • Primary for the one main action of the view, such as "Add entry".
  • Secondary for actions that matter but are not the point of the view, such as "Clear all".
  • Ghost for a quiet action next to a stronger one, such as "Cancel".
  • Danger only when the action destroys something and cannot be undone.

Do not

  • Put two primary buttons in one view. If two actions compete, one of them is secondary.
  • Use danger for destructive-but-recoverable actions. Those take secondary plus a confirmation.
  • Write "Submit" or "OK". The label says what happens: "Add entry", "Delete entry".

Accessibility

  • Always a real <button>, with type="button" unless it submits a form.
  • The focus ring ships with the component. Never remove it.
  • Primary and danger text is white on a 600 or 500 colour: both pass contrast at this size. Check again if a primitive changes.

Input

A single line of text with its label. The label is part of the component, not an optional extra.

Default and filled

States

Focus swaps the border colour for the focus token instead of drawing an outline, so the field reads as "active" without a ring around a ring. Error and disabled states do not exist yet; the first feature that needs one adds the tokens and the story.

Tokens

Component tokenPoints atLive value

Usage

Use

  • Free text that fits on one line: a name, a roaster, an origin.
  • A placeholder as an example of the format, never as the label.

Do not

  • Drop the label to save space. A placeholder disappears the moment someone types.
  • Use it for a fixed set of choices. That is a Select, or the segmented control once it exists.

Accessibility

  • The label's for matches the input's id, so clicking the label focuses the field and screen readers announce it.
  • Placeholder text is a hint, not a requirement. The label carries the meaning.

Select

One choice from a fixed list, when the list is too long for the options to sit side by side.

Default

Tokens

Component tokenPoints atLive value

Usage

Use

  • Six or more options, or options with longer labels.
  • A choice that is set once, inside a form, and submitted with it.

Do not

  • Use it for two to five short options that switch a view instantly. That is the segmented control's job.
  • Leave it without a selected option when a default makes sense.

Accessibility

  • Native <select>: keyboard, screen reader and mobile pickers all come for free. Do not replace it with a custom dropdown.
  • Label wired by for and id, same as Input.

Badge

A status, read at a glance. Pill-shaped, coloured by meaning.

Variants

Tokens

Component tokenPoints atLive value

Usage

Use

  • Status and counts: "3 brews", "Saved", "Unrated".
  • The colour means something. Success is green because it is good news, not because green looked nice.

Do not

  • Use a badge for metadata such as a roast level or an origin. That is a Tag.
  • Make a badge clickable. It reports; it does not act.

Accessibility

  • Each variant pairs a 100 background with a 700 text colour from the same hue, which holds contrast at the small size.
  • The word carries the meaning, the colour reinforces it. Never a colour-only badge.

Tag

A piece of metadata attached to an entry: roast, origin, process. Quiet by design.

Default

Tokens

Component tokenPoints atLive value

Usage

Use

  • Facts about an entry that help you find it again.
  • Several in a row is fine; they are meant to sit together.

Do not

  • Colour a tag to show status. Status is a Badge.
  • Invent a "selected" look for filtering. Filtering is the segmented control's job.

Accessibility

  • Plain text in a span. If tags ever become interactive, they become buttons, and that is a new story.

Card

A bordered surface that groups related content. Brewlog uses it for each entry.

Default

The entry layout inside the card (.entry, .entry__main, .entry__meta) belongs to Brewlog's page styles, not the design system. The card itself is just the surface.

Tokens

Component tokenPoints atLive value

Usage

Use

  • One card per thing in a list: one entry, one brew.
  • Padding comes from the component; content starts at the edge of that padding.

Do not

  • Nest cards. A card inside a card means the inner one should be a plain group.
  • Use a card to decorate a single paragraph. Surfaces group; they do not emphasise.

Accessibility

  • A card is a div. The list it sits in gives the structure (ul and li in Brewlog).
  • The rating inside carries an aria-label because dots alone say nothing to a screen reader.

Alert

A message about the current state of the page: empty, saved, a warning, a problem.

Variants

Tokens

Component tokenPoints atLive value

Usage

Use

  • Info for an empty state, with an invitation to act.
  • Danger for an error, saying what went wrong and how to fix it. No apology, no mystery.

Do not

  • Stack alerts. One at a time, the one that matters now.
  • Use an alert as a heading or a callout for ordinary text.

Accessibility

  • Each variant pairs a light background with a 700 or 800 text colour and holds contrast at body size.
  • An alert that appears after an action should get role="status" so it is announced. Brewlog's empty state is static, so it does not need it.

Rating

Five dots, filled to the score. Dots, never stars: a recorded decision, with its reason in CLAUDE.md.

Scores

Tokens

Component tokenPoints atLive value

Usage

Use

  • How much you liked a brew, on your own scale, in your own journal.
  • Always five dots, so an unrated entry still reads as a rating.

Do not

  • Swap the dots for stars. Stars read as a public review score, and Brewlog is private. Ask for stars and the agent will stop you, with the date of the decision.
  • Make the dots interactive here. Rating is entered through the Select in the form.

Accessibility

  • The aria-label on the group says the score in words. Without it, a screen reader hears five empty spans.
  • Filled and empty differ in lightness, not only in hue, so the score reads without colour.

Adding a component

The same five steps every time, in this order. Each step is checkable; the hook checks the first three for you.

  1. Story first. A Markdown file in stories/: what it is, when to use it and when not, anatomy, states, the tokens it needs, accessibility, acceptance criteria. The segmented control story is the template.
  2. Tokens. Add the component's Layer 2 tokens to component-tokens.css, each pointing at a primitive. Every colour and radius goes through them. A literal value anywhere comes straight back from the hook.
  3. CSS. Add the classes to components.css, using only the new tokens and the shared scales.
  4. Inventory. Add a row to the design-system skill at .claude/skills/design-system/SKILL.md. Until the row exists, the agent treats the component as not existing, which is correct.
  5. This page. Add a section here that looks like the others: stage, snippet, token table, usage, accessibility. Copy the Button section and replace its content. Then move the component's link in the nav out of the pending style.

Then open Brewlog next to this page, change one primitive in tokens.css, and reload both. If the new component moved with everything else, it is part of the system.
